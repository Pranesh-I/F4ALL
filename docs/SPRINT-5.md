# Sprint 5 — Backend Ingest + Server-Side Re-Verification

## Status

Implementation complete. **63 backend tests green**, lint clean, and the API
verified over real HTTP against a live server.

Two things are unproven and both are called out below: the pipeline has not been

## Goal

Uploaded videos are received, stored, and **independently re-scored by the
server** — the thing that makes a result trustworthy rather than a number a
phone reported about itself.

---

## The shape of it

```
 mobile app                     backend                        worker
 ──────────                     ───────                        ──────
 chunked upload ──────> /api/videos/upload/*
                          │  reassemble + verify SHA-256
                          │  store (S3 / local disk)
                        video row
 submit score ────────> /api/tests/submit
                          │  status = processing            ┌──────────────┐
                          └─ queue verification ──────────> │ fetch video  │
                                                            │ MediaPipe    │
                                                            │ re-score     │
                                                            │ compare      │
                                                            └──────┬───────┘
                                                                   ▼
                                                    verified  or  flagged + reason
```

`final_score` is never written by any of this. It is set only when a human
official approves in Sprint 8. A machine result must never be presented as an
official one.

---

## Server-side scoring is a port, not a reimplementation

`app/verification/` mirrors the mobile analyzers file for file. The state
machines, thresholds and rejection rules are identical by design — the server's
job is to reach the same answer *from its own evidence*, not a different answer.

The independence that matters is in the input. The server extracts its own
landmarks from the uploaded video and never trusts the ones the device reported.
A modified client can lie about landmarks; it cannot make a video show a sit-up
that did not happen.

Two deliberate asymmetries:

- The server runs `pose_landmarker_full`, the phone runs `pose_landmarker_lite`.
  The server has no battery or thermal budget, so it uses the better model. It
  is meant to be the superior measurement, not an equal second opinion.
- The server scores the 480p transcode the phone uploaded, not the original.
  That is also what an official reviews.

Both are reasons the two scores can legitimately differ slightly, and why the
discrepancy tolerance is not zero.

## The most important test in this sprint

`tests/test_parity.py` replays canonical pose sequences — generated by the
mobile implementation — through the server's scorers and asserts **identical
scores**.

Why it earns that description: the server auto-flags a submission when its score
disagrees with the device's. That mechanism is what makes an official result
defensible, and it is also the first thing to break if the Kotlin and Python
implementations drift apart. When they drift, the flag fires on athletes who did
nothing wrong, and the reviewer looking at the flag cannot distinguish a real
discrepancy from an implementation gap. The system degrades quietly, in the
direction of punishing honest people.

Two implementations of one algorithm in two languages will drift. The only
question is whether anyone finds out before an athlete does.

Ten fixtures, chosen to cover where divergence actually happens rather than the
happy path — partial reps, rejected too-fast reps, lost tracking, a shallow top
angle near the threshold cliff, and an INVALID case:

| Fixture | Mobile | Server |
|---|---|---|
| situps_5_clean | 5 | 5 |
| situps_10_fast | 10 | 10 |
| situps_3_slow | 3 | 3 |
| situps_partial_rep | 1 | 1 |
| situps_tracking_loss | 1 | 1 |
| situps_shallow_top_angle | 4 | 4 |
| jump_40cm | 39.7339 | 39.7339 |
| jump_15cm | 14.7801 | 14.7801 |
| jump_60cm_tall | 59.6755 | 59.6755 |
| jump_none | INVALID | INVALID |

A second test parses `AnalyzerThresholds.kt` directly and compares all eighteen
constants, catching drift in thresholds no fixture happens to exercise.

CI regenerates the fixtures from the mobile source and **fails if the committed
ones are stale**, so changing mobile scoring without updating the server is a
red build rather than a silent divergence.

## Bug found: a Redis outage hung every submission

Exercising the API against a live server with Redis stopped, `/api/tests/submit`
never returned — the client timed out.

The code already caught broker exceptions and was *written* to degrade to
"verify it later". It did not work, for two independent reasons:

1. Celery's default publish retry **blocks** rather than raising, so the except
   clause was never reached.
2. The far bigger one: the Redis **result backend** has its own 20-attempt retry
   loop, entirely separate from the broker's, and `apply_async` touches it on
   publish. Bounding `broker_transport_options` did nothing for it.

The fix was to delete the result backend entirely. Nothing ever read a task's
return value — verification outcomes are written to PostgreSQL, which is the
system of record. Configuring Redis as a result backend added a second thing
that had to be reachable at publish time, and its retry loop was the thing
hanging the athlete's request.

This mattered more than an ordinary bug because of what fails. A brief Redis
blip would have hung every submission and exhausted the API's workers — an
outage in an optional background queue taking down the endpoint athletes use.
`tests/test_broker_resilience.py` pins the behaviour: a submission is accepted
and durably recorded with the broker unreachable, and lands in `processing`
where `python -m app.cli reverify-pending` will find it.

**A queued job is an optimisation. The database row is the commitment.**

## Contract gap closed

Sprint 4 discovered that `/api/tests/submit` accepted a `video_id` with no
endpoint that produced one, and added four upload endpoints to
`docs/openapi.yaml`. This sprint implements the server half of exactly that
contract — the mobile client was already written against it.

Verified over real HTTP, including the path that matters most:

```
PASS  upload init
PASS  first chunk accepted
PASS  resume reports server-held chunks      <- client asks, server answers
PASS  incomplete upload refused
PASS  complete + checksum verified
PASS  completing twice is idempotent
PASS  submit test
PASS  read result back
PASS  SLA endpoint reports backlog
PASS  dashboard review queue reachable
```

The resume test interrupts after one of three chunks, re-queries the server for
what actually landed, sends only the missing two, and the checksum passing at
the end proves byte-identical reassembly.

## Decisions worth knowing about

**Local-disk storage is the default.** Sprint 0's AWS account does not exist. A
backend that cannot start without cloud credentials cannot be developed or
tested against, so `LocalStorage` and `S3Storage` sit behind one interface —
and selecting local in production raises at startup.

**SQLite-compatible models.** `sqlalchemy.Uuid` and non-native enums rather than
postgresql dialect types, so the whole suite runs in-memory. A test suite that
needs four services running is a test suite people stop running.

**Enums persist their value, not their name.** `values_callable` keeps the
stored strings aligned with the CHECK constraints in `db-schema-v1.md`, and is
required for `FaceVerificationStatus.passed = "pass"`, where name and value
differ because `pass` is a Python keyword.

**`task_acks_late` with `reject_on_worker_lost`.** A worker killed mid-verification
returns the job to the queue. An athlete's test disappearing because a container
restarted is not acceptable.

**Flags carry a reason, a detail and a severity.** A reviewer handed "flagged"
with no explanation cannot act on it. Severity scales with the size of the
disagreement so a queue can be triaged.

**Agreeing scores from poor tracking are still flagged, at low severity.**
Agreement derived from mostly-unusable frames is weak evidence, and without this
a shaky result reaches an official with nothing marking it as shaky.

**A video the server cannot score is flagged, never rejected.** It is not
evidence the athlete did anything wrong.

**Region scoping is enforced in the query and returns 404, not 403.** Confirming
that a result exists in another region leaks information a regional reviewer is
not entitled to.

**Signed, short-lived video URLs only.** These recordings show minors.

## What I could not verify

**PostgreSQL.** Docker Desktop was not running on this machine, so every
database check ran against SQLite. The models avoid dialect-specific types for
exactly this reason and the migration applies cleanly, but *"the migration runs
on Postgres"* is an assumption until someone runs `docker compose up`.

**The end-to-end SLA.** Measuring it needs a Celery worker, a real athlete video
and a stopwatch. The instrumentation is in place; the number is not.

**Real accuracy.** Server scoring is verified to match the mobile implementation
exactly, and the mobile implementation's accuracy against real bodies is still
the open Sprint 3.4 item, blocked on reference videos. Parity means the two
agree — not that either is right.
